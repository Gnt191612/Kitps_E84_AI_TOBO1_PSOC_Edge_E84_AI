# 3D 实时仿真

`tools/sim_3d.html` 的“实时仿真”把真实的 H7 固件放在浏览器里运行，外部世界由模型提供。不接硬件就能拖动人、换场景、拔线，看固件的反应。

| 部分 | 真实程度 | 文件 |
|---|---|---|
| H7 调度、雷达背景和变化检测、云台、目标管理、融合、复锁、接力 | **真实固件源码**，编译成 WebAssembly | `sim_host.c` + `STM32H7/` → `sim_3d/firmware_wasm.js` |
| ESP32 闭环控制量、丢失判定 | 照抄 `ESP32_ov2640/tracking`，测试核对常数 | `sim_3d/world.js` |
| ESP32 图像跟踪 | 模型：目标在视野内且没被挡住就跟得上，加噪声和随机跟丢 | `sim_3d/world.js` |
| 84E 识别 | 模型：准确率取模型评估结果（仅 AI 生成图，未实拍），只算画面里最靠近中心的物体 | `sim_3d/world.js` |
| 超声波、舵机速度、串口、房间 | 模型：参数是按数据手册和经验估的，**都没有实测** | `sim_3d/world.js` |

所以它适合查逻辑问题、试参数方向、排练和判断接错线的现象。发现时间、误差这些数字依赖模型参数，不能当实物性能写进报告。上板实测后，把量到的值填进“仿真”页的参数，模型才会接近实物。

## 怎么用

- **相机画面：** 左下角三个窗口是三块板的摄像头拍到的东西，绿框是跟踪位置，红框是没看到。按“相机画面”可以关掉。
- **射界和接力：** 地面扇形是各云台的射界，亮的是正在跟踪的板。走到边线时弹出接力提示，相机窗口边框颜色表示角色（绿色主跟踪、黄色辅助、蓝色接手），“近边界”表示快到边线。辅助板本来就看着目标，所以接力往往只要几毫秒。
- **84E 边扫描边跟踪：** 雷达发现后 H7 把 84E 云台转过去；84E 连续识别并回传目标在画面中的位置，H7 据此转云台跟着目标；连续 3 帧判为人才认定，把坐标（外推到 ESP32 转到位的时刻）交给 ESP32，之后 84E 停下待命。认定之前 ESP32 不动。开关是 `Core/exp_config.h` 的 `EXP_RECOG_WHILE_TRACK`。
- **批量统计：** 用当前场景、参数和拔线状态换随机种子跑多次，对照开题报告指标。适合比较改动前后，比如先跑一次，改参数或拔一根线再跑一次。结果是模型算的，不能当实测。
- **房间和柜子：** 可以改房间大小（会重新上电重学背景）、加柜子并拖动。只挪柜子不重学，可以看固件怎么应对环境变化。“重新上电”保留自己摆的柜子，点场景按钮则换回场景自带的布置。
- **参数：** 改动自动记在这台电脑上，可以导出成 JSON 发给队友。上板量到实测值后填进来，模型才接近实物。

## 雷达两端

两块 ESP32 在雷达的 ±135° 方向、约 28 cm，正好是舵机的两端。固件不再扫 ±105° 以外（`RADAR_EDGE_IGNORE_DEG = 30`），所以雷达的盲区从背后 90° 变成 150°，“俯视”里绿色扇形以外发现不了人。这个角度按波束半角 15° 估计，上板要测。

## 外观

环境（`sim_3d/scenery.js`）和人物动作只是外观，不参与计算。靠墙设备不单独算回波，路线不能穿过它们（`ENV_CLEAR`，测试会查）。相机窗口看到的是渲染画面，判定仍来自模型，不是对这幅画面做图像识别。导线走线是示意（用细束带扎成束），实际接线以 `WIRING.md` 为准。

## 没有建模的部分

- 真实摄像头画面、光照、图像跟踪算法本身
- 俯仰方向只算到“跟不跟得上”：控制量和方向按固件，跟身体哪一段是假设（画面内最接近身体中段的位置）；水平和俯仰互不影响
- 云台转动时拍的画面会糊，影响 84E 判断和模板跟踪，这里没有建模，要上板看实际效果
- 84E 的模板跟踪按“看得见就跟得上”简化。实物上模板从画面中心建，雷达方位不准时可能盯到背景，这是最需要上板验证的地方
- 84E 每帧判定彼此独立，实物上连续帧的错误往往相关，“连续 3 帧”的效果可能比仿真差
- OV7675 的视场没有查证，先按和 OV2640 相同（50°×38°）处理
- 串口帧的打包解析（`tests/test_protocol.c` 单独测），串口电平问题
- 舵机抖动和负载变化。舵机供电只是估算，见下一节
- 开发板供电：USB 线只画了接法，按永远正常处理。开发板电流、欠压复位、舵机对开发板的干扰都没有算
- 84E 和 ESP32 的固件没有运行，只有 H7 是真实代码

## 舵机供电估算

接线方案见 [WIRING.md](../../WIRING.md) 第 7 节：自制电源分配板，电源 ≥3 A，固件不用改。仿真默认就是这个接法，“仿真”页可以切到面包板做对比。PCA9685 这类 I2C 驱动板要改固件，没有采用，也没有模拟。

重新计算：`node power_report.js`。电流来自 SG90 标称和经验值（转动 0.25 A、启动 0.65 A 持续 40 ms、保持 0.03 A），路径电阻是估计值（面包板 0.5 Ω、驱动板 0.06 Ω），**都没有实测**，所以只看趋势。下面是 2026-11-05 的结果（典型参数，每格 10 次）：

- 正常走路、两人、绕一圈：舵机平均约 0.3 A，峰值约 2.7~3.1 A，超过 1 A 的时间不到 1%。难点是多只舵机同时启动的瞬间，不是持续电流。
- 电源 ≥2 A：跟踪正常。绕一圈最低电压面包板 3.79 V、分配板 4.26 V；电源 3 A 时面包板 4.09 V、分配板 4.89 V。
- 电源 1.5 A：分配板还能正常工作（最低 3.74 V，覆盖 94%），面包板绕一圈约 36% 时间欠压停转，覆盖掉到 45%。
- 电源 1 A：绕一圈严重变差（覆盖 15~18%）。一旦多只舵机同时卡住，就很难恢复。这种卡住的程度取决于模型，实物可能更好也可能更差。

上板前先用万用表测：蓝色升压板带载时的电压和最大电流、单只舵机的转动和堵转电流、面包板电源轨到舵机的压降。把结果填进“仿真”页的参数再看。

## 改了 H7 固件之后

3D 仿真里跑的是编译好的固件，要重新生成：

```bash
python build_firmware.py
```

需要 [wasi-sdk](https://github.com/WebAssembly/wasi-sdk/releases)，解压到仓库根目录的 `.tools/wasi-sdk-13.0`，或用环境变量 `WASI_SDK_PATH` 指定。只有改固件的人需要它，使用软件不需要。

## 测试

```bash
node test_live_sim.js
```

检查内嵌固件是否为当前源码、模型常数是否和 ESP32 固件一致、完整流程、接线故障，并打印跟踪速度表。不需要编译器（检查固件时需要 Python）。

`node try_scene.js intrude 60 typical 1 -v` 可以在命令行跑一个场景并打印事件。

## 仿真发现的固件问题（2026-11-05）

### 已修复，都还没有上板验证

1. **云台跟不上正常走路。** 原来 `closed_loop.c` 的 Kp=0.5 乘 H7 的换算系数（2°/400），每帧只修正约 1.5% 的偏差，理想传感器下 2.4 m 处横穿 80 cm/s 以上就丢。`tests/test_h7_demo_flow.c` 的替身当时用每帧 30%，所以没测出来，现在替身和真实 PID 一致。

   改法：ESP32 的 PID 三个系数都乘 5（Kp=2.5、Ki=0.05、Kd=0.5，每帧修正 7.5%），H7 的 `GIMBAL_CTRL_DEADBAND` 也从 2 改成 10。改 ESP32 而不是加大 H7 的 `GIMBAL_PAN_STEP_MAX`，原因是原来的 Kp 在画面边缘也只输出 75，±400 的范围只用了不到两成；现在基本用满，H7 每帧最多 2° 的保险不变，也不用放宽。死区同比放大，让死区对应的偏差仍是约 0.67°（2 px），否则噪声会一直推云台。

   仿真结果：同样条件下 150 cm/s 能跟住，但这只说明方向对。**振荡没有建模**，上板范围和步骤见 [EXPERIMENTS.md 第 6 节](../../EXPERIMENTS.md)。
2. **主跟踪板无回应时不换板。** 原来 A 板命令线断或死机时，H7 只会一直重发，B 板看得见人，目标却锁不上。现在重发一次仍无回传就改派给另一块板（事件 `FAILOVER`）。另一块板在跟别的目标时不抢，等它空出来再改派；被换下的板不再当辅助板，也不接接力，直到它再回传或点“停止”。接线后的确认步骤见 [EXPERIMENTS.md 第 7 节](../../EXPERIMENTS.md)。

3. **人离得近时同一个人被当成两个目标，辅助板也对不准。** 固件把雷达 (0, 20)、ESP32-A (-20, 0)、ESP32-B (20, 0) 各自看到的方位直接混用，1.3 m 内相差可达 20° 以上。结果 B 板被派去跟“新目标”，没有空闲板可接力，A 板转到极限后跟丢；辅助板的公式也只在 2 m 外碰巧可用。现在先算出目标的平面位置，再按各观测点的位置换算（`BearingFromPoint`、`AssistLocalize_ComputeBearing`）。辅助板看不到目标时每秒重新瞄准一次。

### 还没有处理，需要实测数据

运行测试时第一条会标为“已知问题”。

3. **空房间偶尔出现假候选。** 斜对墙面时回波时有时无、距离随角度变化快，同一格两次测距可差 30 cm 以上。典型参数下 10 分钟约 3 个，再遇到 84E 误报就会去跟不存在的目标。波束和噪声都是估计值，需要实测确认。
4. **单帧跟丢就算丢失。** ESP32 第一帧没跟上就上报 lost，H7 立刻转入丢失流程。按估计的 0.5% 单帧跟丢率，70 秒内约丢失十几次，大多能很快复锁。实际跟丢率要实测。
