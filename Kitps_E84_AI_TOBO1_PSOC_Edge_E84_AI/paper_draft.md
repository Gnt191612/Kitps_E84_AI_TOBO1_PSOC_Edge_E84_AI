# 基于 PSOC Edge E84 多板协作的嵌入式 AI 目标检测与跟踪系统

## 摘要

单一低成本传感器难以同时完成大范围目标发现、语义识别和连续跟踪。本文设计了一种以 Infineon PSOC Edge E84 为识别核心的多板协作系统，采用"雷达发现—NPU 确认—视觉跟踪"三级流程：HC-SR04 超声波传感器由 270° 舵机带动扫描，通过角度分格背景建模检测相对环境的距离变化；KIT_PSE84_AI 在 Ethos-U55 NPU 上对 160×120 灰度全图执行 INT8 人体二分类；两块 ESP32-S3-CAM 使用高梯度区域模板匹配与卡尔曼滤波完成跟踪；STM32H743ZIT6 负责统一调度、资源分配、数据融合和七路舵机控制。系统通过统一的 UART 帧协议互联，支持最多 3 个目标的管理、双目三角定位、预判扫描、边界接力与跟丢复锁。

目前系统已完成三块主控的固件开发和电脑端自动化验证，尚未进行整机上板实验。在 Vela 编译器估算下，模型单帧推理约 13 ms；在按场景留出的 4 折交叉验证中，改进训练后的模型准确率约为 92.5%、误报率约为 7.6%（初版约为 85.8%、20.8%），但仍未达到设计目标（≥95%、≤5%），且训练和测试数据都是 AI 生成图像，真实画面上的精度尚未验证。本文给出系统设计、电脑端验证结果和待上板实测的实验方案。

**关键词：** PSOC Edge E84；Ethos-U55；嵌入式 AI；多板协作；目标跟踪；背景建模；卡尔曼滤波

## 1 引言

### 1.1 研究背景

随着微型神经网络加速器的发展，在资源受限的嵌入式平台上运行深度学习推理已成为可能。PSOC Edge E84 集成 Cortex-M55、Cortex-M33 与 Ethos-U55 NPU，为低功耗视觉推理提供了硬件基础。然而，单一平台的感知能力有限：视觉传感器受视场角和光照约束，超声波传感器无法区分目标类别，云台则存在机械响应延迟。

全国大学生嵌入式芯片与系统设计竞赛（英飞凌赛道）要求基于 KIT_PSE84_AI 构建具有实际应用价值的 AI 系统。本文面向小范围室内场景中的人员发现与持续跟踪需求，将异构的感知与计算资源纳入统一调度框架。

### 1.2 问题与本文工作

本文针对以下四个问题提出相应方案：

| 问题 | 具体表现 | 本文方案 |
|---|---|---|
| 单一感知方式鲁棒性不足 | 超声波无法识别类别；视觉跟踪易受遮挡影响，且视场有限 | 雷达发现、NPU 确认、视觉跟踪分级协作 |
| 超声波易把静物报为目标 | 墙壁和家具同样产生回波 | 角度分格背景建模，只检测"比环境明显变近"的位置 |
| 多目标动态调度困难 | 目标数量变化、穿越云台边界、短时跟丢 | H7 统一管理 ESP32 角色与 84E 请求队列 |
| 板间通信可靠性风险 | 中断与主循环并发访问；协议实现易不一致 | 统一帧协议、环形队列，以及三方源码互通的自动化测试 |

### 1.3 相关工作

- **嵌入式神经网络推理。** TensorFlow Lite Micro 为微控制器提供了轻量推理框架[1]，Ethos-U55 则面向 Cortex-M 系统提供专用加速[2]。
- **雷达与视觉融合。** Wei 等人综述了自动驾驶中毫米波雷达与视觉的融合方法，并将其分为数据级、决策级和特征级[3]。本文的传感器成本与测量能力低得多，采用决策级的分级协作。
- **嵌入式视觉跟踪。** Blanco-Filgueira 等人在 NVIDIA Jetson TX2 上实现了基于深度学习的实时多目标视觉跟踪[4]。本文的跟踪节点算力更低，因此识别交由 NPU，跟踪采用轻量的模板匹配。
- **目标聚类。** DBSCAN 适用于目标数量未知的点云聚类[5]，本系统早期版本曾采用该方法。但单个超声波传感器无法区分墙壁和人，聚类结果仍包含大量静物，因此改用背景建模（见 3.3 节）。

## 2 系统架构

### 2.1 硬件组成

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ HC-SR04+舵机  │  │ KIT_PSE84_AI │  │ ESP32-S3 ×2  │
│ 角度分格背景  │  │ 全图人体     │  │ 模板匹配跟踪  │
│ 变化检测      │  │ 二分类       │  │ 控制量回传    │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       └─────────────────┼─────────────────┘
                         ▼
              ┌─────────────────────┐
              │   STM32H743ZIT6     │
              │ 调度 / 目标管理 / 融合 │
              │ 七路舵机 PWM          │
              └─────────────────────┘
```

| 单元 | 型号 | 主要配置 | 职责 |
|---|---|---|---|
| 主控 | STM32H743ZIT6（鹿小班 LXB743ZI-P1） | Cortex-M7，当前配置 200 MHz（HSI，芯片最高 480 MHz），2 MB Flash | 调度、雷达处理、融合、舵机控制 |
| 识别 | KIT_PSE84_AI（PSE846GPS2DBZC4A） | Cortex-M55 + M33 + Ethos-U55，OV7675 DVP | 全图人体二分类 |
| 跟踪 ×2 | GOOUUU ESP32-S3-CAM N16R8 | 双核 240 MHz，16 MB Flash，8 MB PSRAM，OV2640 | 模板匹配跟踪、PID 控制量计算 |
| 雷达 | HC-SR04 + 270° 位置舵机 | 标称量程 2 cm~4 m | 大范围目标发现 |
| 执行 | SG90 9G ×7 | 水平 270° ×4，俯仰 180° ×3 | 雷达扫描与三路云台 |

### 2.2 工作流程

1. **发现。** 雷达以 135°→0°→135°→270°→135° 的顺序往复扫描，每段 3 s，每 70 ms 测距一次，并将结果与背景比较，输出候选目标。
2. **确认。** H7 把 84E 云台转向候选方位，并发送识别命令；84E 采集一帧，经 NPU 推理后返回置信度。请求排队执行，超时时间为 1.5 s。判为非人体的位置 5 s 内不再送识别，并将其距离并入雷达背景。
3. **跟踪。** 确认后，H7 按云台可视范围选择空闲的 ESP32，下发相对其云台朝向的偏移角；ESP32 在该位置建立模板并逐帧跟踪，回传位置和控制量，由 H7 统一输出 PWM。
4. **协同。** 单目标时，另一块 ESP32 担任辅助观察，用于三角定位；目标接近云台边界时，由另一块 ESP32 接手；目标丢失时，按复锁流程恢复。雷达在跟踪期间持续运行，以便发现新目标。

### 2.3 统一坐标系

系统以 ESP32-A 指向 ESP32-B 的方向为 $+X$，以正前方为 $+Y$，单位为 cm。方位角 $\theta$ 以正前方为 0°，顺时针为正。方位角与云台角的换算关系为：

$$\text{Pan} = 135^\circ + \theta - \theta_{\text{mount}}$$

其中 $\theta_{\text{mount}}$ 为各云台的安装朝向，当前设置为 A = −90°、B = +90°、84E = 0°，需按实物安装确认。

## 3 核心方法

### 3.1 调度模型

H7 在单一主循环中运行，不使用 RTOS，以雷达处理、84E 识别、ESP32 跟踪三个逻辑进程轮转。中断只负责接收数据和写入环形队列，回调在主循环中同步执行，因而无需为共享状态加锁。

每块 ESP32 的角色由 H7 管理：

| 角色 | 含义 | 进入条件 |
|---|---|---|
| IDLE | 空闲 | 上电，或目标已释放 |
| TRACK | 主跟踪，其结果用于控制云台和更新目标 | 目标经 84E 确认，且该板可视范围覆盖目标 |
| ASSIST | 辅助观察，其结果只用于三角定位，丢失时不删除目标 | 仅有单目标，且另一块板空闲 |
| HANDOVER | 接手边界目标，锁定后转为主跟踪 | 主跟踪板的 Pan 到达 15° 或 255° |

系统最多管理 3 个目标，目标 ID 保持稳定，不随列表位置变化。两块 ESP32 均被占用时，第三个目标由 H7 记录并上报。

为避免重复分配，落在已跟踪目标 ±20°、±80 cm 范围内的雷达候选被视为同一目标。此外，系统支持 `STOP`/`START`/`STATUS` 串口命令，停机时所有云台回到初始朝向。

### 3.2 NPU 全图推理

**模型与部署。** 模型输入为 160×120×1 灰度图，输出背景和人体两类，使用全整数 INT8 量化。系统基于 Infineon 官方 ModusToolbox 多核工程部署，由 CM55 通过官方机器学习工具链调用 Ethos-U55。生成产物中 45 个算子全部运行于 NPU，量化模型约 126 KB，经 Vela 编译后约 179 KB，张量内存约 157 KB。

**训练方法。** 初版模型的训练结果不稳定，且跨场景误报率高。改进版在不增加数据的前提下，加入 BatchNorm、两类均衡采样和改进的早停策略以稳定训练，并通过缩小人物模拟远距离目标、大幅裁剪背景图以增加背景多样性。摄像头噪声仿真和加宽网络在现有数据上没有带来可确认的提升，未被采用。

**预处理。** 摄像头输出 320×240 BGR565 图像，转换为灰度后，经 2×2 平均缩小到 160×120，再做量化：

$$x_{\text{int8}} = x_{\text{gray}} - 128$$

**输出解释。** 输出量化参数为 scale = 1/256、zero point = −128，人体概率为：

$$p_{\text{human}} = \frac{q_{\text{human}} + 128}{256}$$

**一致性核查。** 浮点模型、uint8 输入输出模型和 int8 输入输出模型在全部 496 张图像上的判定完全一致；类别下标、灰度公式和量化参数在训练端与板端也一致。因此，当前的精度差距来自模型和数据，而非量化或部署环节。

### 3.3 雷达目标发现

**非阻塞测距。** TRIG 发出触发脉冲后立即返回，ECHO 由 TIM3 通道 1 输入捕获。由于 TIM3 同时输出三路云台 PWM，测距时不能清零计数器，脉宽由两次捕获的差值并结合毫秒时基计算得到。距离为：

$$d = \frac{v_{\text{sound}} \cdot t_{\text{echo}}}{2}$$

无回波或超量程记为"该方向量程内无物体"，不视为有效测量点。

**背景学习。** 将 0°~270° 按 5° 分格。上电后每格采样 3 次，取中值作为背景距离 $b_i$。学习期间，扫描范围内不应有人。

**变化检测。** 第 $i$ 格的测量值 $d_i$ 满足下式时，该格记为变化格：

$$\min(b_i,\ 400\ \text{cm}) - d_i \geq 30\ \text{cm}$$

背景取上限是因为量程边缘的回波时有时无，否则无回波方向上约 3.9 m 的墙面会被误报为目标。

相邻且距离相差小于 50 cm 的变化格合并为一个候选；孤立的单格需连续两次成立才算候选。距离小于 20 cm 的候选被忽略。

**背景更新。** 未变化的格缓慢跟随环境：

$$b_i \leftarrow (1-\alpha)\, b_i + \alpha\, d_i,\quad \alpha = 0.05$$

84E 判为非人体的候选，其方位 ±10° 内的当前距离直接并入背景。

### 3.4 视觉跟踪

**建模。** ESP32 以 H7 下发的方位换算出种子像素，在 64×48 窗口内按 3×2 网格计算梯度能量，选取梯度最强的 3 个区域，保存为 16×16 模板。

**匹配。** 每个模板在 ±8 像素范围内最小化绝对差之和：

$$(\Delta x^*, \Delta y^*) = \arg\min_{\Delta x, \Delta y} \sum_{(u,v)} \left| I_t(u+\Delta x, v+\Delta y) - T(u,v) \right|$$

三个区域的位移经离群剔除后合成目标位移；匹配良好时，模板缓慢更新以适应外观变化。

**滤波与控制。** 使用状态量为 $[x, y, v_x, v_y]^T$ 的卡尔曼滤波平滑位置和估计速度，当前过程噪声 $Q = 10$、测量噪声 $R = 4$。这组参数仅在合成画面上整定。控制量由 PID 计算（$K_p = 0.5$，$K_i = 0.01$，$K_d = 0.1$，待整定），回传给 H7 执行。

**丢失与复锁。** 连续 5 帧匹配失败判为丢失，随后用目标自身的模板按 16、32、64 像素逐级扩大搜索范围。ESP32 未能恢复时，由 H7 按预测方位发起复锁，每 500 ms 一次，最多 5 次，仍失败则释放目标。

### 3.5 融合、预判与接力

**统一融合。** 雷达、84E 和 ESP32 的观测都换算为"观测点 + 方位 + 距离"，再转换到统一平面坐标后融合。

**三角定位。** 设两块 ESP32 的位置为 $P_A$、$P_B$（基线 0.4 m），方位角为 $\theta_A$、$\theta_B$，方向向量 $\mathbf{u}(\theta) = (\sin\theta, \cos\theta)$。目标位置由两条射线求交：

$$P_A + s\,\mathbf{u}(\theta_A) = P_B + r\,\mathbf{u}(\theta_B),\quad s, r > 0$$

两路观测的时间差超过 150 ms 或两条射线发散时，不输出结果。

**预判扫描。** H7 为每个目标维护一组卡尔曼滤波，将方位外推到"云台到位 + 推理完成"的时刻，并使 84E 提前转向该位置；方位波动越大，扫描窗越宽。

**边界接力。** 主跟踪板的 Pan 到达 15° 或 255° 时，H7 将另一块空闲的 ESP32 预置到目标方位；新板锁定后释放原板，原板回到 135°。3 s 内未锁定则取消接力。

### 3.6 板间通信

三路独立 UART（115200 bps，8N1）使用统一帧格式：

| 字段 | 偏移 | 长度 | 说明 |
|---|---|---|---|
| Header | +0 | 2 B | 0xAA 0x55 |
| Length | +2 | 1 B | Type 与 Payload 的总字节数 |
| Type | +3 | 1 B | 帧类型 |
| Payload | +4 | $L$ B | 载荷（最大 64 B） |
| Checksum | +4+$L$ | 1 B | 对 Type 和 Payload 逐字节异或 |

| 链路 | Type | 载荷字段 | 载荷长度 | 总帧长 |
|---|---|---|---|---|
| H7→84E | 0x01 | 命令、目标 ID、中心角、宽度、最小/最大距离、时间戳 | 22 B | 27 B |
| 84E→H7 | 0x02 | 目标 ID、置信度、x、y、距离、角度 | 21 B | 26 B |
| H7→ESP32 | 0x02 | 命令、目标 ID、两个参数 | 10 B | 15 B |
| ESP32→H7 | 0x02 | 目标 ID、x、y、Pan、Tilt、丢失标志 | 18 B | 23 B |

接收端采用单生产者单消费者环形队列：中断只写队尾，主循环只读队头。KIT_PSE84_AI 的 UART 引脚属于 1.8 V 电源域，与 H7 之间须加双向电平转换器。

## 4 验证与分析

> 本节数据分为三类：**电脑端测试结果**、**理论估算**和**设计目标**。整机实验尚未开展，下文所有数值都不代表上板实测结果。

### 4.1 电脑端自动化测试

测试使用 gcc 编译真实固件源码，只替换硬件抽象层、串口和雷达测量，并通过故意改坏代码确认测试能够发现回归。当前测试全部通过。

| 测试 | 覆盖内容 | 结果 |
|---|---|---|
| H7 调度器 | 单目标、辅助板丢失、复锁成功/失败、非人体并入背景、人体判定阈值、通信统计输出、三目标、停机/恢复、84E 超时、边界接力（共 11 个场景） | 全部通过 |
| 整机流程仿真 | 真实调度器和雷达模块，测距、84E、ESP32 由虚拟房间替身计算：学习背景、发现锁定、接力、第二目标、遮挡复锁、排除静物、停止恢复、重新学习 | 全部通过 |
| H7 单元 | 雷达背景学习与人体检测（墙、柜子、门口、噪声）、脉宽跨周期换算、三角定位 | 全部通过 |
| ESP32 跟踪 | 移动目标、强纹理背景、小目标、静止抖动、遮挡复锁 | 合成画面最大误差约 2.6 像素（远处小目标约 3.3 像素），静止无抖动 |
| 三方协议 | H7、ESP32、84E 帧互通，乱码、校验错误、交错发送、长文本、错误计数（32 项检查） | 全部通过 |

在合成画面上，三高特征区域匹配的单帧耗时约为 32×32 全图匹配的五分之一（一次电脑测试中约 0.18 ms 对 1.0 ms）。绝对值随电脑负载变化，只有相对差距可参考，不代表 ESP32-S3 上的实际耗时。

测试和代码审查发现并修复了若干缺陷，下表列出其中影响较大的部分。这也说明，仅靠编译通过无法发现此类问题：

| 缺陷 | 后果 | 修复 |
|---|---|---|
| ESP32 帧解析少收一个负载字节 | H7 发出的所有命令都被丢弃 | 修正负载计数 |
| H7 未开启串口与定时器中断，启动文件向量表有误 | 依赖中断的通信和测距无法工作 | 改用 ST 标准启动文件，补齐中断处理和优先级配置 |
| 卡尔曼参数过度平滑 | 目标转向时滞后 3~4 像素 | 调整 $Q$、$R$ |
| 速度预测误用两帧前的位置 | 速度估计偏大一倍 | 改用相邻帧 |
| H7 与 84E 的人体判定阈值不一致（0.3 与 0.5） | 84E 判为背景的画面可能被 H7 当作人体跟踪 | 统一为 0.5，并增加回归测试 |
| 锁定首个目标后雷达停止 | 无法发现第二个目标 | 雷达改为每轮主循环运行 |
| 量程边缘的回波被当作变化 | 空房间也报假目标（由整机流程仿真发现） | 变化检测时背景按 4 m 封顶 |

### 4.2 模型评估

数据集为 16 个场景共 496 张 AI 生成的灰度图像（人体 320 张、背景 176 张），并非 OV7675 实拍。跨场景结果按 4 折交叉验证合并统计，每个模型重复 3 次取平均，阈值为 0.5。

| 模型与评估方式 | 样本数 | 准确率 | 误报率 | 漏检率 |
|---|---|---|---|---|
| 初版，随机划分验证集（与训练集场景相同） | 100 | 90.0% | 5.6% | 12.5% |
| 初版，按场景留出 | 496 | 85.8% | 20.8% | 10.5% |
| **改进版（INT8），按场景留出** | 496 | **92.5%** | **7.6%** | **7.5%** |
| 改进版（INT8），按场景留出，阈值 0.6 | 496 | 92.1% | 5.5% | 9.3% |

随机划分的结果偏乐观，因为验证集和训练集来自相同的场景，而且验证集还用于选择模型；按场景留出的结果更接近泛化能力。即便如此，它测试的仍是同一类 AI 生成图像，换到真实摄像头后精度预计还会下降。

改进版的结果来自选定方案之后用新随机种子进行的复测，不含选型时的成绩；选型阶段同一方案曾测得 94.2%，存在挑选偏差，未作为正式结果。三次复测的准确率为 90.9%~94.4%，个别场景组的误报率达到 20.5%，因此 1~2 个百分点以内的差别不具有参考意义。训练稳定性也有改善：初版在 3 次评估中出现 13 次塌缩（全判人体），改进版为 0 次。

当前工程的阈值为 0.5。阈值 0.6 可降低误报，但也使漏检增加，且该结果同样来自 AI 生成图像，因此阈值留待实拍数据确定。

### 4.3 延迟估算

下表为理论估算，云台和跟踪耗时都有待实测。

| 符号 | 含义 | 估算值 | 依据 |
|---|---|---|---|
| $T_{\text{radar}}$ | 单次测距 | 70 ms | 测距间隔上限 |
| $T_{\text{proc}}$ | 雷达数据处理 | 1 ms | 假设值 |
| $T_{\text{cmd}}$ | H7→84E 帧 | 2.3 ms | 27 B @ 115200 bps |
| $T_{\text{gimbal}}$ | 84E 云台转动 60° | 300 ms | 舵机标称速度 |
| $T_{\text{cap}}$ | OV7675 一帧 | 33 ms | 按 30 fps |
| $T_{\text{npu}}$ | NPU 推理 | 13~50 ms | Vela 估算 ~ 设计上限 |
| $T_{\text{res}}$ | 84E→H7 帧 | 2.3 ms | 26 B @ 115200 bps |
| $T_{\text{esp}}$ | H7→ESP32 帧 + 一帧采集 + 跟踪 + 回传 | 58.3 ms | 1.3 + 40（按 25 fps）+ 15（假设）+ 2.0 |

从候选出现到首次跟踪结果，串行累加的延迟为：

$$T_{\text{lock}} = T_{\text{radar}} + T_{\text{proc}} + T_{\text{cmd}} + T_{\text{gimbal}} + T_{\text{cap}} + T_{\text{npu}} + T_{\text{res}} + T_{\text{esp}} \approx 480 \sim 517\ \text{ms}$$

该估算与 500 ms 的设计目标相当，上限略超。云台转动约占 58%~63%，是主要瓶颈；预判扫描和转角较小的情况有助于降低这一项。

整机流程仿真计入了 84E 和 ESP32 云台的实际转动等待后，发现到锁定约为 1.1~1.5 s，高于上述估算和设计目标。仿真中的云台速度来自固件配置，并非实测，但说明 500 ms 的目标很可能需要预先转向等优化，或者按目标与云台的初始夹角分情况评估。

需要说明，上式未包含雷达扫到目标之前的等待时间，也未计入 ESP32 云台的转动时间（后者已由上面的仿真计入）。按每段 3 s 的扫描方式，同一方位两次被扫到的间隔最长约 12 s，因此发现延迟主要取决于扫描周期，应在实验中单独统计。

### 4.4 通信带宽

单字节传输时间为 $10 / 115200 \approx 86.8\ \mu\text{s}$。下表按各链路独立计算利用率：

| 链路 | 帧长 | 单帧时间 | 假设帧率 | 利用率 |
|---|---|---|---|---|
| H7→84E | 27 B | 2.3 ms | 5 帧/s | 约 1.2% |
| 84E→H7 | 26 B | 2.3 ms | 5 帧/s | 约 1.1% |
| ESP32→H7（每路） | 23 B | 2.0 ms | 30 帧/s | 约 6.0% |

按当前帧长和假设帧率，串口带宽不构成瓶颈。

## 5 讨论

**多板协作的收益与代价。** 分级协作使每一级都使用最适合的传感器与算力，但也带来了通信延迟、协议一致性和联调复杂度等代价。超声波扫描周期可能决定发现速度，而 84E 的串行识别可能在多候选时形成瓶颈，这两点都需要实验验证。

**数据是当前的主要瓶颈。** 模型评估表明，量化和部署没有带来精度损失，差距主要来自数据。实拍数据采集工具已经实现，下一步应使用 OV7675 实拍数据重新训练，并按场景或采集批次划分测试集。改进训练方法使跨场景准确率提升了约 7 个百分点，但这些结果都来自同一类 AI 生成图像，摄像头噪声和暗光的影响也测不出来，不能代替实拍验证。

**验证方法。** 电脑端测试发现了多个仅靠编译无法暴露的缺陷，说明在硬件联调前进行软件级验证是有价值的。但合成画面和模拟硬件无法反映光照、舵机滞后、机械抖动和电气干扰，不能替代实物实验。

### 5.1 局限性

- 超声波波束较宽（约 15°~30°），角度分辨率有限，且量程不超过 4 m，不适用于远距离或高速目标。
- 背景学习要求上电时扫描范围内无人，静止目标也可能被逐渐吸收进背景。
- 160×120 分辨率下，远距离小目标更难识别，当前错例也集中于远处小人物、蹲姿和头部出画的情况。
- H7 调度为非抢占式，单个处理步骤过长会影响其他进程。
- 模型目前基于 AI 生成图像训练，真实场景精度未知。

### 5.2 后续工作

1. 按 H7、ESP32、84E 的顺序逐块单板上电验证，再进行板间联调。
2. 取得 H7 开发板原理图，核对板载 LED、按键、TF 卡座等的引脚占用；确认 84E J5 排针的引脚序号。
3. 逐只标定舵机脉宽，确认舵机电源规格，并实测堵转和峰值电流。
4. 确认云台安装朝向与图像方向符号，整定雷达和跟踪阈值。
5. 采集 OV7675 实拍数据，重新训练并评估模型。

## 6 结论

本文设计并实现了一套基于 PSOC Edge E84 的多板协作目标检测与跟踪系统的软件，提出了雷达背景变化检测、NPU 全图确认、模板匹配跟踪和 H7 统一调度相结合的方案。电脑端自动化测试验证了调度逻辑、协议互通和跟踪算法在模拟条件下的行为，模型评估也明确了当前的主要差距在于训练数据。系统的整机性能仍有待上板实验检验。
